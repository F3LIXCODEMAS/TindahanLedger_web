4.1.1 Performance Requirements

Table 4.1. Proposed performance requirements for TindahanLedger
Requirement ID System Feature or Module Performance Requirement and Timing Relationship Design Rationale
PERF-01 Owner and Super Admin authentication [PROPOSED TARGET — FOR APPROVAL] Complete a valid login request and return the authenticated redirect within 2 seconds at p95, excluding the user's network transit time. Login throttling and active-account checks must remain enforced and must not be bypassed to meet the target. Authentication gates all protected owner/admin operations; a measurable response limit supports routine use while retaining credential checks and throttle behavior. The target must be tested on the approved runtime and hardware.
PERF-02 Customer management [PROPOSED TARGET — FOR APPROVAL] Complete customer list, detail, create, or update requests within 2 seconds at p95 for an agreed store/customer dataset size. Customer information is used repeatedly in ledger operations. An explicit dataset size is needed because listing and retrieval time depends on database volume and pagination.
PERF-03 Credit transaction recording [PROPOSED TARGET — FOR APPROVAL] Validate and persist a valid credit, enforce the credit-limit rule, and complete the database transaction within 2 seconds at p95 for an approved workload. Measure the complete request-to-response time separately because a configured synchronous receipt attempt occurs after the financial transaction. The credit and its structured purchase items, when present, must remain in the same database transaction. The LedgerService validates balances under a customer lock and persists credit-related records transactionally. Performance must not be achieved by skipping financial checks or returning success before persistence completes. The owner-visible response includes the mail attempt, so both transaction and full-request durations must be recorded.
PERF-04 Payment recording [PROPOSED TARGET — FOR APPROVAL] Validate, allocate a valid payment to outstanding entries, update the balance and any completed debt-cycle record, and complete the database transaction within 2 seconds at p95 for an approved workload. Measure the complete request-to-response time separately because a configured synchronous receipt attempt occurs after the financial transaction. Payment allocation and the updated balance must be consistent. The timing test must include the actual ledger size and database engine rather than measuring only a simple page response.
PERF-05 Running balance and financial summary [PROPOSED TARGET — FOR APPROVAL] Return the customer financial summary and paginated ledger view within 1 second at p95 for an agreed number of ledger entries. Owners and customers need timely balance information. The actual history size and database engine must be stated when validating the target.
PERF-06 Product catalog [PROPOSED TARGET — FOR APPROVAL] Return a product listing or product-search response within 1 second at p95 for an agreed catalog size and query. Product selection supports credit and cash purchase recording. The target should be checked for both catalog browsing and the transaction picker, not inferred from a single static page.
PERF-07 Cash purchase recording [PROPOSED TARGET — FOR APPROVAL] Validate and persist a cash purchase containing up to the implemented maximum of 50 distinct products, then return its result within 2 seconds at p95, excluding client rendering and network transit. The request path calculates line totals from validated quantities/prices and verifies the reviewed total. The 50-item maximum is present in LedgerService::MAX_PURCHASE_ITEMS; the elapsed-time limit is not an approved project specification.
PERF-08 Customer self-service QR portal [PROPOSED TARGET — FOR APPROVAL] Resolve a valid QR credential and return the read-only portal page within 2 seconds at p95 for an agreed customer-history size. The portal's 15-minute inactivity setting must continue to apply. Timely read-only access is useful to customers, but the limit must be evaluated without weakening token validation, revocation checks, store-status checks, or session expiration.
PERF-09 Gmail SMTP notifications The Gmail mailer is configured with a 15-second transport timeout (app/Services/MailDeliveryService.php). This is a code-configured ceiling for an SMTP attempt, not a measured delivery guarantee. [NEEDS VERIFICATION] Record end-to-end attempt duration, application response impact, failure/retry behavior, and actual delivery only after authorized credentials and a controlled test are available. Receipt and reminder mail can depend on an external SMTP service. The transport attempt must be distinguished from financial persistence; a successful SMTP handoff does not establish arrival in a recipient's inbox.
PERF-10 Suki Points earning, cycle completion, and redemption [PROPOSED TARGET — FOR APPROVAL] Complete the database transaction for point earning, debt-cycle completion, or a valid redemption within 2 seconds at p95 (the same proposed transaction target as PERF-03/PERF-04). Record full request-to-response time separately where synchronous mail is also sent. Each balance, payment allocation, point change, and cycle record must remain atomic. Loyalty calculations affect financial and points records. The timing criterion should be measured on the full transaction and cannot justify separating related writes into inconsistent states.
PERF-11 Product recommendations during transaction entry [PROPOSED TARGET — FOR APPROVAL] Complete a recommendation request for a basket of up to 50 product IDs within 250 milliseconds at p95, using the documented benchmark workload of 300 active products and a 12,000-rule active set as the initial comparison fixture. Revalidate the target on the approved target environment before acceptance. The picker requests suggestions while an owner edits a basket. Existing README measurements report a 52.4 ms HTTP p95 for 50 basket products in one in-process MariaDB 10.4.32 development benchmark, with 5 queries; this is a local observation, not an accepted target or production guarantee.

4.1.2 Safety Requirements

Table 4.2. Safety requirements for TindahanLedger
Requirement ID Potential Hazard or Loss Scenario System Safeguard and Required Action Prevented Action or Constraint
SAFE-01 An incorrect outstanding balance is displayed or used to make a credit decision. LedgerService calculates money in integer cents through Money, applies payment allocations and balance changes in a database transaction, and locks the customer row during financial updates. The application must report validation or persistence failure rather than confirm an uncommitted transaction. A credit whose projected outstanding balance exceeds the customer's credit limit is rejected; a payment exceeding the applicable outstanding amount is rejected.
SAFE-02 Repeated submission or a retry records the same payment more than once. Payment requests require a UUID idempotency key. A unique database constraint and LedgerService replay handling return the prior payment batch for a repeated key instead of applying the same submission again. Duplicate application of a payment submission with the same idempotency key is prevented by the database/service path. The key must not be treated as proof that two different keys represent the same real-world cash receipt.
SAFE-03 An erroneous amount, unsupported product, or stale total creates an incorrect credit or sale. Server-side Form Requests validate positive, two-decimal monetary amounts; transaction services perform financial checks, verify catalog/store ownership, calculate line totals, and compare the submitted expected cash-sale total with the server total. Credit records and any structured purchase details are written together. Zero/negative amounts, credit-limit overrun, invalid item data, duplicate product rows, inactive/out-of-store products, and a mismatched cash-sale total are rejected. Product descriptions do not silently change the amount of a credit.
SAFE-04 Deleting a customer or transaction removes history needed to explain balances or disputes. Foreign keys use restrictive deletion for financial history and dependent records, including credit/payment relationships, Suki Point history, debt-cycle records, and purchase history. The user must resolve dependent records through an authorized, documented retention process rather than bypassing constraints. A customer, credit, payment, product, or rule set with protected dependent history cannot be deleted through the constrained relationships. A backup/restore process is not evidenced and must not be assumed.
SAFE-05 Suki Points are over-redeemed, redeemed against no debt, or deducted more than once. The redemption request validates a positive whole-number point amount. LedgerService::redeemSukiPoints locks the customer and points records, checks available points and debt, records the redemption/payment allocation and point transaction atomically, and recognizes a repeat idempotency key. Redemption above the available point balance or outstanding debt, redemption against a zero balance, and repeat deduction under the same idempotency key are rejected/prevented.
SAFE-06 An unauthorized person changes or views customer financial records. Owner routes require authentication, changed-password status, and the store-owner role; customer and ledger policies check store ownership. Super Admin routes use a separate role. The system must retain these controls on all financial read/write routes and deny cross-store requests. Guest, wrong-role, and cross-store customer actions are denied. A suspended store is read-only for the protected transaction routes; a customer cannot write through the read-only QR portal.
SAFE-07 Hardware, host, or database failure causes loss of financial records. Financial writes use database transactions and relational constraints to avoid partial application of the covered transaction. Operators must establish, document, and test backups, recovery steps, and access controls before using production financial records. No claim is made that database transactions alone prevent loss caused by disk failure, deletion, ransomware, or unavailable infrastructure. Until an approved recovery process exists, production readiness for this hazard remains [NEEDS VERIFICATION].
SAFE-08 A late-fee policy change alters the terms of an already recorded credit, or a duplicate penalty is applied. The credit stores the accepted policy snapshot; a penalty is a separate linked ledger entry with a unique link to the original credit. Changes to a store policy do not rewrite historical snapshots. A second penalty for the same credit is prevented by the unique relationship. Existing credits without the relevant snapshot are not to be silently reinterpreted as covered by a later policy.
SAFE-09 A customer or owner revisits an old payment confirmation and is shown a historical remaining/previous balance calculated from transactions recorded later. The inspected fallback in PaymentController::confirmation derives prior/remaining balances from the customer's current balance when the original session receipt is absent. [NEEDS VERIFICATION / CORRECTIVE ACTION] Before treating a revisited confirmation as a historical receipt, persist an immutable batch receipt snapshot or display only values that remain derivable from that batch. Verify with a test that records later credits/payments before reopening the earlier confirmation. Do not present a balance affected by later transactions as the balance immediately after an older payment. This safeguard is not established by the current fallback.

4.1.3 Security Requirements

Table 4.3. Security requirements for TindahanLedger
Requirement ID Security or Privacy Domain Authentication and Protection Requirement Policy or Standard Alignment
SEC-01 Owner and administrator authentication Require an authenticated active account for protected routes. Enforce role checks for Store Owner and Super Admin routes. The login flow normalizes usernames, limits repeated failed attempts (five attempts per throttle window in the inspected controller), regenerates the session after authentication, and requires an administrator-issued temporary password to be changed before ordinary use. Password reset and multi-factor authentication were not established as implemented features. Compare authentication design with NIST SP 800-63B-4 (NIST, 2025) and the authentication requirements in OWASP ASVS 5.0.0. This comparison is not a conformance claim.
SEC-02 Password storage and handling Store passwords through Laravel's hashed model cast and exclude password and remember-token fields from model serialization. Do not log, expose, or return passwords. Continue to require server-side password-change validation for temporary credentials. The selected production hashing configuration and password-strength policy require deployment/configuration verification. NIST SP 800-63B-4; OWASP ASVS 5.0.0. Verify the actual production configuration before asserting alignment.
SEC-03 Session protection and request forgery Regenerate the session on successful owner login and QR portal access; invalidate it and regenerate the CSRF token on logout. The application uses Laravel's web routes, which apply the framework's web middleware protections. Private portal responses set no-store, private, and no-referrer headers. Effective cookie flags, HTTPS enforcement, and production session-store protection depend on deployment configuration and require verification. OWASP ASVS 5.0.0 session-management and request-protection controls; NIST SP 800-63B-4 for authentication-session considerations.
SEC-04 Store/tenant isolation and authorization Derive the owner's store from the authenticated user rather than trusting a client-supplied store identifier. Scope customer/product/transaction access to that store, authorize customer and ledger access through policies, and enforce role restrictions. Composite foreign keys in migrations enforce selected customer/store and transaction ownership relationships. OWASP ASVS 5.0.0 access-control requirements. Cross-store denial is also covered by TenantIsolationTest.php; this does not replace a full authorization review.
SEC-05 Customer QR portal credential Treat a QR code as a bearer credential: possession grants access but does not verify the holder's identity. Generate a random token, store its SHA-256 lookup hash and encrypted printable token, revoke replaced codes, remove the encrypted token on revocation, and check credential/store status and a configured 15-minute idle timeout on portal access. Place the QR token in the URL fragment; private headers are applied to portal pages. The token must not be described as password or identity-based authentication. OWASP ASVS 5.0.0 access-control/session requirements; privacy risk review under the applicable data-protection policy. QR issuance/revocation and portal behavior have feature tests.
SEC-06 Customer financial-data confidentiality Limit owner access to customers in the owner's store and expose only the customer's read-only ledger through an active portal session. Prevent caching and referrer leakage on private portal routes. Require HTTPS, suitable storage/access controls, a privacy notice, and a retention/disposal policy in the deployed service; these operational requirements are not verified by repository code alone. Republic Act No. 10173 (Data Privacy Act of 2012) and National Privacy Commission guidance may be relevant to personal-data processing in the Philippines; applicability and compliance require legal/organizational review. OWASP ASVS 5.0.0 is a technical comparison baseline.
SEC-07 Input validation and data integrity Validate untrusted request fields server-side using Laravel validation/Form Requests and apply business-rule checks in transaction services. Preserve store/customer ownership constraints and require positive monetary values, valid UUID idempotency keys, and bounded purchase-item lists on the inspected financial paths. Review all endpoints, background commands, and imports to ensure the same controls apply. OWASP ASVS 5.0.0 input-validation and data-protection requirements.
SEC-08 SQL injection and output encoding Use bound Eloquent/query-builder operations for the inspected financial and portal data paths; do not concatenate untrusted input into raw SQL. Continue to use context-appropriate output escaping in Blade. A repository-wide query/output-encoding assessment and security test report were not produced for this documentation task. OWASP ASVS 5.0.0 injection-prevention and output-encoding requirements. No claim of complete injection immunity is made.
SEC-09 Gmail SMTP credentials and notification data Store the owner's SMTP App Password using Laravel's encrypted cast and hide it from model serialization. The Gmail mailer uses port 587 with required TLS and a configured 15-second timeout; failure logs are designed to mask recipient/sensitive values. Validate customer recipient addresses and send credit/payment receipts only after the financial service returns. Protect production APP_KEY, SMTP settings, logs, and transport configuration. Real Gmail delivery and production secret management were not verified. OWASP ASVS 5.0.0 secrets/communications requirements; NIST guidance for credential handling where applicable. Mail transport configuration is not proof of inbox delivery or end-to-end confidentiality.
SEC-10 Administrative and financial changes Separate Super Admin and Store Owner roles, restrict management routes by middleware, and use the audit logger for recorded administrative actions. Confirm that sensitive financial adjustments, policy waivers, credential issuance/revocation, and administrative changes are authorized and logged with appropriate actor/context without storing secrets. Audit coverage and retention require verification. OWASP ASVS 5.0.0 access-control and logging requirements; applicable organizational privacy and record-retention policies.

4.2.8 Database Normalization

Table 4.8. Functional dependencies and normalization implications in TindahanLedger
Relation and determinant Functional dependency supported by keys or business rules Normalization implication
customers customer_id → store_id, full_name, contact_number, email, residential_landmark, credit_limit, current_balance. For a non-null email, (store_id, email) → customer_id is enforced by a unique index. Customer profile facts are kept in one customer record rather than repeated in each credit or payment. Email uniqueness is tenant-scoped; nullable email means the alternate dependency applies only when populated.
ledger_entries ledger_entry_id → customer_id, kind, amount, transaction_date, repayment_deadline, running_balance, note, penalty fields. A non-null penalty_for_entry_id is unique. Each ledger row describes one credit or penalty for a customer. The unique self-reference permits at most one penalty entry per underlying entry.
payments payment_id → ledger_entry_id, customer_id, amount, kind, payment_date, payment_batch_id, note. A non-null idempotency_key is unique. Also, ledger_entry_id → customer_id in ledger_entries. The payment's customer_id is functionally derivable from its ledger entry, so it is a transitive/repeated value for a given allocation. The composite (ledger_entry_id, customer_id) foreign key intentionally stores and checks both to prevent mismatched-customer allocations.
purchases and purchase_items purchase_id → store_id, customer_id, ledger_entry_id, purchase_type, purchase_date. (purchase_id, product_id) → quantity, product_name_snapshot, unit_price_snapshot, line_total, store_id is unique at item level. Header/detail separation removes repeating product groups. store_id in purchase_items is also determined by purchase_id; it is retained for composite same-store foreign keys. Snapshot name and price represent values at the historical sale, not current products values.
suki_point_transactions payment_id → customer_id, transaction_type, paid_amount_cents, points_awarded, points_redeemed, redeemed_amount_cents, remainder values; payment_id is unique. Customer identity can be derived through the payment, so storing both identifiers duplicates a dependency. The migrations separately reference both rows; service logic associates the right customer and payment, but no composite customer/payment FK was found for this relation.
products product_id → store_id, name, normalized_name, unit_price, description, status; (store_id, normalized_name) → product_id is unique. Product facts are maintained in the catalog once. Purchase item snapshots remain intentionally independent so later catalog edits do not rewrite historical records.
